建造系统由我起头开发，工作同时覆盖 gameplay 与配套 UI；建造物件的交互逻辑和面板也是我参与开发、维护的内容。共享 UI 与 gameplay 基础设施由团队共同维护。

本案例围绕三个核心决策展开：**让操作符合当前输入与世界状态；把制造限制转为有用的下一步；复用界面能力，但保留物件自己的业务规则。**

## 复用边界：为什么加工台独立、储存界面共享

加工台的装备进化关系、物品分类及按装备类型变化的排版具有特殊性，而且会频繁迭代。这些变化主要局限在加工台内部，因此我保留专用面板，复用底层控件与服务，而不是把装备规则扩散进所有建造物件共用的界面。

储存箱可能有很多种，外观可以不同，但容器、槽位和道具数据高度一致。我把复用边界放在背包式子面板与固定配置输入上，让展示形式变化，而物品数据和操作语义保持稳定。当前节选保留的是箱子与背包两侧的独立绑定逻辑、共同数据约定和部分配置行为，不代表完整通用子面板实现已全部公开。

缺材料时仍应打开追踪入口：从制作配方的材料数据进入共享追踪子页，形成统一体验，而不是每个加工台各做一套。`WorkBenchProduct:OnBtnMake` 的普通配方与强化配方分支都保留了这个关系。

关键词：scope of change · specialised composition · shared inventory contract · consistent recovery flow。[完整决策叙述（英文）](DECISIONS.md)。

## 案例一：建造操作需要同时理解界面与世界状态

**背景与问题。** 玩家从目录选择物件，在三维世界调整位置和旋转，再确认放置。目录选择、手持预览、按钮和快捷键必须表达同一个意图；切换分类需要清理旧选择，其他面板打开时也不能误触建造命令。

**实现。** `BuildSpaceModel` 协调目录和选择，再把对象交给原生放置系统。特殊目录项可提供自己的选择／取消回调。原生流程处理位置检测、条件检查和可用操作，Lua 根据操作摘要呈现控件。

`Flow_UpdateOperationUI` 将旋转、取消、有效／无效建造、移动、拆除、修理等操作编码为 bitmask，只在变化时通知 Lua。PC 快捷键还要检查当前输入类型、建造 HUD 状态、原生模式以及具体操作位。

**重要取舍。** 无效建造状态也接收确认动作，因为玩家需要知道失败原因。但 `RequestSpawnUnit` 会先检查有效性，不满足时显示原因并返回。这里分开了“允许尝试并获得反馈”和“允许创建物件”。

**结果。** 建造规则、输入上下文和界面操作通过明确契约连接起来。bitmask 便于比较并减少重复通知，但不能代替原生校验，也不包含所有模式的完整状态。

关键词：operation mask · input context · placement validity · actionable feedback。

## 案例二：装备台——主操作区应该告诉玩家下一步能做什么

**背景与问题。** 装备台同时呈现产品分类、制造路线、选中装备的信息与材料。玩家可能正在选配方、等待制造、处理暂停、领取产物，或者解决等级与材料限制。一个统一的灰色按钮无法准确表达这些含义。

**我的工作范围。** 建造物件交互及配套 UI 的开发、维护是我工作的一部分。这里围绕团队既有系统中的实际产品控件、面板和模型，解释制造操作的完整调用路径。

### 先判断已有生产，再判断新制造的条件

`WorkBenchProduct:RefreshProductBtnGroupForMake` 按明确顺序处理：

1. 没有选中的制造 ID：隐藏主按钮。
2. 原生状态为生产中：显示生产／取消操作，并启动状态轮询。
3. 生产暂停：显示生产／取消操作，不启动该轮询。
4. 有产物可领取：切换到领取操作。
5. 其余情况再检查等级、材料、携带上限，以及本地制造／开始状态。

因此，在已有选中制造 ID 的前提下，缺少下一次制造的材料不应该遮住已有产物的领取入口。原生查询代表当前物件的生产状态，模型中的 eligibility 字段代表当前配方条件，两者不能混为一谈。

### 区分“不能制造”和“没有任何可执行动作”

- **工作台等级不足**：显示等级要求，按钮仍可点击，进入携带当前工作台 GUID 的升级引导。
- **缺少材料**：按钮仍可点击，进入配方材料追踪；强化分支还传递对应等级与追踪类型。
- **达到携带上限**：按钮禁用，模型层也阻止直接调用时开始制造。

这让错误原因与恢复路径连接起来：enabled 表示存在有意义的操作，不一定表示会立即制造。

### 从控件一直追到执行边界

符合条件的点击经过：

`WorkBenchProduct:OnBtnMake` → 制造点击事件 → `WorkBenchPanel:OnBtnMake` → `WorkBenchModel:OnMakeClicked` → `func_MyMakeStart`。

面板根据分类与首次制作经验状态决定是否需要确认；模型检查当前动作和制造条件。如果已经在本地制造，则走打断路径。

开始制造又分为两条：

- **原生队列生产**：提交制造 ID、数量及作为材料的装备实例，然后隐藏面板。
- **本地进度制作**：初始化本地状态，调用原生进度条，刷新控件、动画和当前制造 ID。

取消和领取使用独立处理函数，并保留当前物件 GUID；UI 不直接生成产物。关闭界面后的生命周期也随制作路径不同而不同，不能把隐藏面板等同于取消原生队列。

### 根据真实状态更新，不靠本地时间推断完成

生产变化事件刷新主操作区；生产期间还通过 scope 管理的一秒轮询读取原生状态。虽然方法名含 `CountDown`，保留的实现实际上在检查状态，而不是计算可见倒计时。

只有原生数据表示可以领取时才切换到领取。生产停止且没有产物时重新计算操作，不因本地显示时间结束而发奖。

**结果与取舍。** 主操作区把制造、取消、领取与条件引导连接起来，并沿用既有 UMG／Lua 工作流。代价是状态分布在产品控件、面板、模型和原生查询之间，数字 switcher 索引也依赖控件约定。未来可以考虑集中表达 action 与 reason，但这是改进方向，不是声称已经做过的重构。

[英文详细案例](WORKBENCH_INTERACTIONS.md) · [实际方法的测试](../tests/test_workbench_actions.py)

关键词：primary-action state · eligibility versus production state · recovery actions · command routing · native collectability。

## 案例三：储存箱——不同手势汇入一致的转移语义

**背景与问题。** 双击、详情操作、拖放和批量存取最终操作同一份容器数据。界面变化不能替代真实转移结果，离开或切换箱子也会改变操作上下文。

**实现。** `BoxModel` 保留箱子身份并派发命令；主面板组合箱子与背包等视图，处理距离检查和结束交互。原生拖放入口区分箱内换位、移出、移入以及玩家自身容器之间移动。快速放入和拖入使用共同的放入校验与请求接口，界面从容器数据更新读取结果。

**结果与取舍。** 手势属于呈现层，物品转移的含义属于命令路径。稳定且为正的容量下，储存视图复用槽位记录并刷新可见条目，避免每次清空重建；但仍扫描全部槽位，不是增量差分算法。[刷新成本说明](PERFORMANCE.md)

关键词：gesture versus command · container routing · structural reuse · world-bound lifetime。

## 案例四：武器架——共用选择面板，保留专用规则

**背景与问题。** 武器架需要展示候选物品、数量和选择操作。共用面板不应该了解每个架子的兼容规则、来源容器和占用状态。

**实现。** 适配层按配置筛选物品，从背包和快捷栏收集候选，并保留容器类型与槽位。它向 `AdditionModel / AdditionFrame` 提供标题、列表和交互上下文；共用层处理呈现、选择事件和关闭，适配层处理专用命令与占用反馈。

**结果与取舍。** 共享的是“呈现并选择候选物品”的稳定契约，物品规则仍归物件处理。异步打开、切换架子和过期点击需要检查身份与生命周期；当前代码中的具体检查点集中记录在[详细案例](SHARED_INTERACTIONS.md)和[问题定位](DEBUGGING.md)。

关键词：shared presentation · object-specific adapter · source-item identity · context lifetime。
