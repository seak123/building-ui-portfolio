# 建造与物件交互 UI：从放置到使用

[英文首页](../README.md) · [完整案例](CASE_STUDY.md) · [架构](ARCHITECTURE.md) · [代码路线](CODE_TOUR.md) · [刷新与性能](PERFORMANCE.md) · [问题定位](DEBUGGING.md) · [测试](TESTING.md)

本案例根据个人工作记录及相关实现整理。建造系统由我起头开发，工作同时覆盖 gameplay 与配套 UI；建造物件的交互逻辑和面板也是我参与开发、维护的内容。共享 UI 与 gameplay 基础设施由团队共同维护。

案例沿着三个连续的使用场景展开：**选择并放置物件 → 使用加工台生产 → 使用储存箱管理物品**。这里的加工台具体选取半成品生产界面，不混同于另一个装备打造／强化工作台模块。

## 案例一：建造操作需要同时理解界面与世界状态

**背景与问题。** 玩家从目录选择物件，在三维世界里调整位置和旋转，再确认放置。目录选择、手持预览、按钮和快捷键必须表达同一个操作意图；换分类后不能继续操作旧对象，打开其他界面后也不能误触建造命令。

**实现。** `BuildSpaceModel` 协调目录和物件选择，再把选中对象交给原生放置系统。取消或切换选择时清理手持对象；特殊目录项可以提供自己的选择／取消回调。原生流程负责位置检测、条件检查和可用操作汇总，Lua 负责呈现。

`Flow_UpdateOperationUI` 把旋转、取消、有效／无效建造、移动、拆除、修理等操作编码为 bitmask；只有与上次不同才发出通知。Lua 根据这个摘要显示控件，不在每个按钮中重复整套空间规则。

PC 操作还需要经过三层检查：当前使用 PC 交互、当前处于建造 HUD 状态、原生模式允许操作。之后才检查具体操作位。界面能显示某个按钮，不等于这个快捷键在所有上下文中都应该生效。

**一个重要细节。** 无效建造状态也会接收确认动作，因为玩家需要知道为什么不能建。确认进入原生请求路径后，`RequestSpawnUnit` 先检查有效性；不满足时显示失败原因并返回，不发送创建请求。这里分开了“允许尝试并得到反馈”和“允许真正创建”。

**结果与取舍。** 建造规则、输入上下文和 UI 操作有了清晰的连接。bitmask 能减少重复通知，但它不是所有状态的完整模型，也不能代替原生校验。枚举的一致性、失败原因与 UI 展示仍需要共同维护。

技术要点：operation mask · input context · placement validity · actionable feedback · native validation。

## 案例二：加工台不是一张配方列表，而是一套生产流程

**背景与问题。** 有配方不代表现在能做：它可能尚未解锁、等级条件不够、材料不足，或者生产队列已经满了。只显示一个灰色按钮无法告诉玩家下一步做什么。

**实现。** 打开界面时传递物件配置 ID、实例 GUID 和交互 ID。模型先筛选可展示配方，再按配置、解锁、制作条件和材料的顺序派生状态；面板结合队列容量决定主按钮含义。修改数量后重新计算材料和状态。

材料不足时主操作变为材料追踪；队列满时禁止追加；条件不满足时显示具体要求。真正制造时把物件 GUID、交互、配方和数量交给原生请求接口。领取则传递队列槽位，不由 UI 直接生成物品。

**进度与生命周期。** 队列条目根据原生工作量和速率平滑推进显示，重新收到工作信息时可以校正；暂停、完成与正在工作分开处理。视觉进度到达终点不代表可以发奖，领取仍查询原生可领取数量。面板只响应自己的 GUID／交互对应的离开事件，队列刷新也过滤 GUID；销毁时清理数量控件和 Tick 绑定。

**结果与取舍。** UI 不只是展示限制，而是把限制转为合理的下一步。配方状态与主按钮状态分属不同层，解锁状态还影响独立的界面切换，不能把单一按钮函数当作全部校验。延迟响应、对象消失以及零工作量等边界需要进一步的运行时验证。

技术要点：recipe eligibility · primary-action state · object identity · queue state · presentation interpolation。

## 案例三：储存箱的不同操作方式应汇入相同语义

**背景与问题。** 玩家可能双击、打开物品详情、拖放或批量存取。不同手势最终操作的是同一份容器数据；本地按钮显示成功，不等于实际转移已经完成。切换箱子和离开范围也会改变交互对象。

**实现。** `BoxModel` 持有当前箱子的身份并派发命令；主界面组合箱子、背包和其他容器子界面。定时距离检查负责离开范围后隐藏面板，销毁流程请求结束交互。

原生拖放入口根据源／目标容器区分四条路径：箱内换位、移出箱子、移入箱子以及玩家自身容器之间移动。快速放入和拖入最终使用共同的放入校验与请求接口；界面从容器更新读取结果，而不是自行把显示变化当成成功。

选取的服务端快速取出函数还检查箱子是否允许取出，以及私人箱子的请求者身份。这是用于解释 UI 与原生请求边界的一段实现，不代表整个库存安全性已经被本案例验证。

技术要点：gesture versus command · container routing · request versus acknowledgement · world-bound lifetime。

## 刷新优化：保留结构，更新内容

储存箱的 `SetContainerInfo` 不会在每次物品变化时都清空列表。

- 首次创建或容量改变：重建槽位记录，并逐项加入原生列表。
- 容量相同且为正：保留已有记录，更新物品 ID，再刷新当前显示条目的 behaviour。

这减少了稳定容量路径上的列表清空、重新插入和数据包装工作。但它仍遍历所有槽位，因此不是只更新差异项的算法；更不能直接推导出具体 FPS 或内存收益。相同容量也不自动等于相同箱子，切换对象的生命周期仍需验证。

建造操作摘要只在变化时通知 Lua，也是明确的工作量控制；原生位置检测仍可能逐帧发生。加工进度使用本地显示插值，则需要把显示更新成本与真实工作状态更新分开测量。

技术要点：structural reuse · displayed-entry refresh · change detection · cost boundaries。

## 通用框架与专用界面的边界

共用的是 UMG／Lua 绑定、异步创建、列表数据桥接、资源加载与事件机制；不强行共用的是放置、生产和容器转移各自的操作规则。这样策划可以围绕规则与反馈迭代，美术继续搭建控件和动画，工程侧维护稳定的数据及生命周期契约。
